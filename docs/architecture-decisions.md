# Architecture Decisions (Living Constitution)

> This is the detail log extracted from [`CLAUDE.md`](../CLAUDE.md) § "Decisions & Lessons Learned". The rules for maintaining it live there. The `/challenge` skill appends here automatically when its verdict is `PROCEED` for an architectural decision.
>
> **Rules:** keep entries tight (1–3 sentences); always include the **reason** and a **reconsider-if** condition; failed experiments go in the second subsection.

## Architecture Decisions

- **[2026-10] MCP sessions shared across relay pods through a Redis directory of session ids, not credentials** (#39634, PROCEED after two REVISE rounds and one REDESIGN; [`docs/mcp-sessions.md`](mcp-sessions.md)): Chose a Redis hash per caller session (MCP server URL → session id + integration id) and a shared last-used sorted set, so any relay pod continues or closes any session. A pod closing a session reloads the integration's credentials from Postgres, checking the account and the stored URL. Store selection is a relay-only setting (`MCP_SESSION_STORE`), default `redis` since validation on dev (a forgotten per-env opt-in left dev split across pods); `memory` only for installs without Redis. Why: medium/large installs run 2 relay pods with no affinity, so the per-pod in-memory map silently split one chat across two upstream sessions. Rejected: forwarding calls to the pod that opened the session (a session id is portable, unlike an agent's websocket); encrypted credentials in Redis (a new place where secrets live). Counterarguments accepted: about 2 Redis round trips per MCP call; a Redis outage falls back to per-pod behaviour, visible as an error log and a metric; a session whose server restarts is silently replaced. Reconsider if: relay sessions need affinity for another reason, or MCP credentials move out of integration configs.
- **[2026-10] Post-answer critiques continue the planner's own request instead of sending standalone prompts** (#39803 / #39633, PROCEED after one REVISE round; `llm/llm-server/agents/core/critique_continuation.go`, setting `llm_critique_mode=continuation`, which also replaces the two claim-critique on/off flags with one mode: off | audit | guided | continuation): On ReAct4, the answer critique, the claim audit and the audit's guidance call are sent as the planner's request exactly as last sent (same messages, tools, options and model) plus its final answer and a reviewer instruction, so the provider's prompt cache covers the investigation and the critiques see earlier refinement rounds. Before this, each critique round sent ~155k input tokens (answer critique ~65k, audit ~45k, guidance ~45k) with 0% cached while the tool loop ran 90–95% cached, and the stateless critique re-offered alternatives it had rejected one round earlier. Kept both critiques: in 14 days the answer critique alone sent back 24 answers the claim audit passed (stopped early, recommended commands it could run, missing incident window), so they check different things. Counterarguments considered: compressed evidence (compression starts at 75% of the window and never fired on Gemini in a 850-packet sample; a compressed run uses the standalone path); provider plumbing (tool settings are left unchanged so the cached prefix stays identical, JSON mode is not used, and a tool call or unparseable reply falls back to the standalone critique); the critic reading the planner's reasoning (offline replay on 82 labelled answers: verdicts agreed with the standalone audit as often as the audit agrees with itself, and it flagged more weak claims, not fewer). The audit cites the planner's evidence ids through an index in its instruction. ReAct3 keeps the standalone path. Made the default in 2026-10 after a day on dev: 119 rounds, 3 fallbacks (one Gemini 503, two audit timeouts), cost per review round $0.089 → $0.033, refine rate unchanged (12.0% vs 12.4%); the two replaced flags were removed. Reconsider if: the critiques run on a different model from the planner, cached tokens per critique call stay low on dev, or the continuation's refine rate drifts from the standalone audit's.
- **[2026-10] A signal class is scoped to the resource for an ownerless Kubernetes Service or workload, not to its namespace** (`api-server/services/triage/signal_class.go` `classSubject.identity`, #39560, PROCEED after one REVISE round): Chose `namespace/name` as the class scope when the alerted subject has no owner and is a Service, Deployment, StatefulSet or DaemonSet, over the namespace fallback (one verdict for every Service in a namespace, minted from whichever fired first) and over the bare name (the same name in two namespaces would share a verdict). The same function supplies the subject line of the classifier prompt, so the prompt cannot describe a different subject from the one the verdict is cached under; cloud-provider sources are excluded because ECS and Cloud Run alerts also use subject type `service`. The class key carries no version, so verdict rows cached under the old namespace scope for these kinds are left unused: do not join older `score_factors.class_key` values to current rows. Reconsider if: mint volume per tenant becomes a cost problem, or catch-all aggregation keys (one key covering many alert kinds) are split, which would want a versioned key.
- **[2026-10] A tool call on another connected account behaves exactly like one on the conversation's own account, only resolved and executed there** (#38596 / #38588, PROCEED on v3 after two REVISE rounds; `tools.ResolveToolCallTarget`, `api/workspace_proxy.go`): For integration-backed tools (Postgres, Redis, RabbitMQ), the one per-call resolver picks the integration from the target account's own integrations (an ambiguous name there is refused, the origin's configs are never a fallback), the workspace token is bound to the target, and the workspace proxy looks the config up in, and relays to, that account. The same classifier and approval flow apply as on the origin; only access is checked on the target (read to run, write for a write). Rejected: a reads-only gate and a SQL allowlist for cross-account calls. The read/write weaknesses they addressed (no Postgres classifier, LLM-only SSH classification, approvals keyed per tool) exist on the origin too and belong to the approval/security work (#39880, #38827), not to cross-account execution. Counterarguments considered: a write approved on one database is reused for another in the same conversation (already true within one account); cross-account config selection decided in several places (mitigated: one resolver, proxy as the enforcement point). Reconsider if: target-scoped approvals land, or a cross-account path is found that bypasses the resolver or the proxy.
- **[2026-10] Per-host DB branding is EE-only, enforced by the OSS strip, not a runtime check** (`api-server/services/ee/branding/`, `api-server/services/branding/product_name.go`, `app/src/ee/actions.yaml`, `notifications-server/notifications_server/configs/branding_overrides.py`; PROCEED after one REVISE round): Chose to move the `tenant_branding_override` reader, admin actions and `/v1/branding/overrides` route into the stripped `ee/` tree, leaving OSS a one-function `branding.ProductName()` seam that EE fills with a resolver from `init()`, over gating writes on a licence feature or edition flag. Why: the frontend already drew the boundary at the strip (`app/src/ee/branding/serverInit.ts` records that a licence gate on branding once reverted partner UIs to the house brand), and before this the backend half still shipped to OSS, so an OSS super-admin could rebrand emails and chat while the UI stayed Nudgebee. Counterarguments considered: moving the whole package broke five OSS callers of `ProductName` (hence the seam); stripping actions via `oss-patches.sh` would fork the convention (hence `app/src/ee/actions.yaml`); notifications-server has no `ee/` tree, so its refresher treats a 404 from the absent route as the OSS state and logs it once. Migration V925 stays in OSS, so the table exists but is empty and an OSS→EE upgrade needs no schema step. Reconsider if: OSS should offer branding, in which case move the package back out of `ee/` rather than adding a flag.
- **[2026-10] An agent finding closes as "recovered" only on stored evidence that the pods have stayed up, and the collector's rule mirrors the agent's** (k8s-collector `close_events_for_recovered_workloads`, `_workloads_not_yet_stable`; #38238, PROCEED after one REVISE round): Chose to hold a workload's open agent findings unless every container of every live pod is ready and has been running for 10 minutes (60 after an OOM kill), read from the stored pod rows when the close runs, over the restart-count delta between snapshots it replaces. Why: the agent sends Pod, ReplicaSet and Deployment changes as separate requests in no fixed order, so a check that needs the pods to arrive with the workload never runs on the request that says "1/1 ready" — the delta guard was live and a crashlooping Deployment's alert still closed within a minute. The two windows are the agent's own (`podCrashLoopStableWindow`, and the OOM matcher's one-hour rate limit): closing sooner than the agent would re-raise leaves a broken workload with no alert. Unknown holds — no container status from an older agent, or no pod stored yet — so older agents get no recovery close until they are upgraded. Counterarguments considered: this is a second definition of "recovered" beside the agent's (accepted as a mirror, pinned by a test, until the agent sends its own resolve); a workload fixed by a rollout no longer closes within seconds but on the first workload report after the window, usually the next periodic snapshot (accepted: the agent suppresses a re-raise for that same window); findings that involve no restart, such as probe warnings, close as before. Reconsider if: the agent emits a RESOLVED when its recovery predicate passes — this close then becomes the fallback for agents that predate it.

- **[2026-09] The automation builder learns execution rules from tool outputs, not system-prompt prose** (runbook-server Run Script runtime notes, `/workflows/validate` warnings; llm-server workflow builder): Chose to carry "where each executor runs and as whom", account types and login-code detection in task runtime notes, in coded validate warnings that the builder must clear, and in account data supplied to the prompt. The alternative was adding rules to the builder system prompt, which the agent had already quoted and broken. The system prompt keeps at most a few generic rules. Why: validation errors are the one channel the agent reliably loops on, and the same warnings reach people editing in the UI. Login code in scripts entered through manual edits as well as agent edits. Counterarguments considered: TypeScript mirrors of the server rules can drift (mitigated with a Go-generated fixture and a jest parity test), and a warnings field is an additive API change. Reconsider if: the builder still ignores validate warnings in evals, or warnings grow into a second, unowned rule system.
- **[2026-09] Code-fix ownership is best-effort and separate from publication (#39037, PROCEED):** The code-analysis orchestrator resolves the newest eligible human author from pre-fix provider history, then publishes before assigning and verifying. Passing an assignee to creation was rejected because CLI identity/metadata errors could block an otherwise authorized PR, and GitHub assignment is a separate API operation anyway. Ownership travels in the result so same-chat GitHub/GitLab companion issues can reuse it without replacing explicit/existing assignees; unresolved identities leave artifacts open with a warning. Provider history avoids shallow-clone boundary attribution; lookup is bounded to 100 candidate identities and 30 seconds, with changes over 100 paths left unassigned rather than partially sampled. Reconsider if private-email resolution failures warrant a tenant-managed identity map or companion assignment needs deterministic workflow enforcement instead of agent instructions.

- **[2026-09] Atlas uses `public` first and repairs only the known role-schema tables on upgrade** (`api-server/migrations/run-migrations.sh`, `reconcile-role-schema.sql`, #39267): PostgreSQL's default `"$user", public` put 15 application tables in `nudgebee` for a dedicated `nudgebee` database role; later migrations explicitly address `public`, so changing Atlas's path alone cannot complete that upgrade. The job moves only those known tables, only for that role, in one transaction with a short lock timeout and conflict checks, then runs Atlas with `public` first; existing app connections can resolve the moved tables through their unchanged fallback path, while a busy table leaves the move uncommitted for retry. Reconsider if another role/schema combination is observed or if application SQL explicitly addresses the old schema, which would need a separately scoped migration and compatibility plan.

- **[2026-09-27] Explicit child targets are scoped intent; execution tools apply them as defaults** (`llm/llm-server/agents/core/factory_agent.go`, `tools/delegated_target_input.go`, #38588): Live handoffs showed that a specialist could drop a named account between planner and tool call, so target-aware children now carry one validated, agent-scoped connection identity while each execution tool decides whether and how to apply it; explicit per-call selection still wins, and authorization and write approval remain at the concrete tool boundary. Account-bound specialists without a target contract are not made cross-account by this handoff, and opaque multi-command shell writes remain blocked rather than guessed. Reconsider if those specialists gain per-call targeting or a runtime command proxy can safely bind each invocation independently.
- **[2026-09] An LLM integration's one configured fallback is a slot, either referenced or owned — never a model string resolved against whatever credentials exist** (`llm/llm-server/agents/core/llm_config.go`, `api-server/services/integrations/llm.go`, `app/src/components/llm/AddLLMConfigModal.jsx`; #36339): Chose one fallback per integration with two explicit shapes — a reference to an existing slot (`llm_fallback_ref_source` + `llm_fallback_ref_model`, resolved by the same reader pinned requests use, visibility enforced per account) or a fallback-owned slot (`llm_fallback_*`, read by a dedicated scope that inherits nothing from the integration: no global creds, OAuth, headers, deployment or thinking flag) — over a `provider:model` qualifier in the legacy fallback list, which borrowed credentials from any slot naming that provider and could carry the primary's OAuth secret or headers to another endpoint. Legacy comma lists keep their exact behaviour and run first; the configured fallback runs last. Counterarguments considered: a cross-integration reference has no referential integrity (disabling or re-linking the referenced integration breaks it silently until runtime/Test Connection) — accepted for v1; Test Connection now resolves references through the runtime resolver per account, so it authorizes every forwarded account and bypasses the integration cache. Reconsider if: broken references show up in practice (add a referenced-by guard on the referenced integration's save/disable), or per-tier configured fallbacks are requested.
- **[2026-09] A dropped RabbitMQ message is an error, and the webhook table is the recovery record** (`api-server/services/common/mq.go`, `api-server/services/integrations/core/webhook_recovery.go`, `runbook-server/internal/system/cron_triggers.yaml`): Publishing to an exchange with no bound queue is discarded by the broker and still confirmed, so `MqPublish` returned nil while the payload was gone — on dev this silently dropped 17 GitHub CI deliveries over three hours (RabbitMQ pod recreated, `webhook_process` queue never re-declared, `event_incoming_webhooks` rows stuck at `processing_status='pending'`). Three layers, chosen together because each covers a failure the others miss: (1) opt-in `MqPublishWithMandatory` publishes in confirm mode with the mandatory flag and correlates `basic.return` by message id through a bounded registry, so the webhook handler's existing sync fallback actually fires — the return is dispatched on another goroutine, hence an explicit 150ms grace window after the confirm rather than relying on AMQP's return-before-ack ordering; (2) `MqConsume` no longer gives up permanently when its first dial fails, so a pod that starts while the broker is down still declares its queue (this was the root cause — the worker restarted in the same minute RabbitMQ was rebuilt); (3) a 5-minute `Stuck Webhook Recovery` cron re-drives rows left `pending` for 10 minutes or stranded in `processing` for 30, which is the only layer that covers a message that routed fine, waited in a queue nobody was draining, and aged out at its 1h TTL. Counterarguments considered: mandatory-plus-returns alone would have missed most of the outage window (queue present, consumer dead); publisher-side queue declaration was rejected because go-rabbitmq v0.16.1 does not expose it and declaring a queue per routing key would create undrained queues on fanout exchanges. Reconsider if: a second publisher needs unroutable detection, at which point the grace window belongs behind a metric rather than a constant.
- **[2026-09] Automation-written evidence declares a display type, and api-server builds the card** (`api-server/services/event/authored_evidence.go`, `runbook-server/internal/tasks/events/add_evidence.go`, `app/src/pages/investigate.jsx`): The `events.add_evidence` step offers only the types the Investigate page can draw — markdown, json, table — and every such card is stamped `additional_info.actual_action_name = "workflow_evidence"`, with the page switching on the element's own `type` from there. Chose one owned dispatch key over each type borrowing the action name of an enricher that happens to render the same way (an authored card previously had to claim to be `text_enricher`, and a card whose name matched nothing saved fine and then rendered nothing, silently). api-server validates and shapes the envelope, so a type or payload the page cannot draw is refused at run time rather than stored: rows must be arrays, non-scalar cells are flattened, and JSON must be an object or array, because each of those reaches the page as a React child and throws for every viewer of the event. Counterarguments considered: the type enum now exists on both sides of the RPC and in the page's switch, and the singular `evidence` request shape 400s against an api-server older than the runbook-server sending it — deploy order is api-server first. Reconsider if: a fourth type is wanted (`diff` and `file` both already have producers), at which point the set is worth serving from one place rather than restating in three.
- **[2026-09] Inventory changes reach the knowledge graph through a 10-minute watermark detector plus per-resource refs; the account rebuild stays the unit of correctness** (`api-server/services/knowledge_graph/changedetect`, `resourcepatch`, #37921): The detector compares per-account active counts and newest create times with saved marks of the same column (dev stores `timestamp` columns shifted against `timestamptz`, so cross-table comparisons are wrong) and requests account rebuilds; rollouts and cloud events become per-resource refs that the consumer applies only when the source's own builder reproduces the stored node's id and type, otherwise folding them into an account rebuild. Rejected: change detection in the collectors (duplicates the graph's include rules in Python, misses relay-fetched kinds); comparing inventory timestamps with build-queue timestamps; an in-process ticker in every replica; widening the events job's re-list to "updated" (Azure reports every metric alert as an update); `updated_at`/`last_seen` for deletions (re-flipped dead rows bump `updated_at` tens of thousands of times a day). Patches and builds of a tenant are mutually exclusive: a patch holds the same transaction-scoped `kg_build:<tenant>` advisory lock that claiming takes, for its whole check-read-write, so a running build makes it stand aside and no build can be claimed until it has written (a version check at write time was rejected — it would touch `SaveNodes`, which every source uses). Patched rows are also stamped one version ahead so a build claimed right after cannot sweep them (cost: a node deleted right after a patch is tombstoned one build later); the detector visits tenants and accounts least-recently-probed first, from the marks' own `updated_at`, so a run that hits its time budget cannot starve the same tenants every time; and per-resource patching sits behind `kg_resource_patch_enabled`, which turns every ref into an account rebuild when false. It shipped off so patched output could be compared with rebuilds on a live environment first; two days on dev showed the opposite — the detector ran every 10 minutes across 156 tenants and published 103 refs, but with the switch off not one reached the patch path (zero `resourcepatch` log lines), so the comparison could never happen and the only thing exercised was the fallback. It now defaults on, and remains a switch that restores rebuilds without a deploy; a delete tombstones all incident edges, including behavioural ones the sweeps leave to time-based expiry. Reconsider if GCP gains a change feed (GCP updates are rebuild-only today) or more cloud modules move onto per-resource edge rules, which would widen the edge-patching set. Deletes are resolved per resource (the nodes whose inventory row went inactive are tombstoned with every incident edge, as correct as a rebuild) and new resources of *creatable* types are added per resource; connected types (EC2, RDS, VMs, load balancers, VPC/subnet/NIC, IAM, K8s workloads and nodes) still rebuild the account, because a single-row build cannot produce the edges other resources point at them (LB targets, EBS/ENI attachments, K8s node→EC2) and a fast but incomplete topology gives wrong blast-radius answers. A created node gets its own-row outgoing edges immediately; incoming and live-CLI edges arrive with the next account build. Every per-resource rule is a `PatchSpec` declared in the resource's own file and assembled by a per-cloud policy, so the applier and detector hold no resource knowledge; a drift test (update and create modes) and a per-cloud spec test are what keep the declarations true. No Azure type is creatable: its row-driven reference passes emit outgoing edges from ordinary resources using a whole-account index. Reconsider creatability of connected types if their incoming edges become derivable from the target's own row.

- **[2026-09] Design-system drift is gated at import level by diffing each changed file against its merge-base version — no baseline file, no token regex** (`app/scripts/check-ds.js`, renamed from `check-ds-imports.js`; `app/package.json` `lint2`, #37432): The check fails when a PR into `main` adds an import of a raw MUI component with a `ds/*` replacement or of a legacy component, parsed with the `typescript` compiler API (multi-line, aliased, re-export and dynamic imports resolve exactly). Why: ~300 files already carry drift, and cleaned files regress (`optimise-new/DetailsPanel` went back to MUI `Divider` two days after its migration — the check catches that replay); import names are precise enough to fail on, where a regex over `sx` values is not. Replaying ~700 merges to `main` (26 Aug–14 Sep) it would have flagged 4 imports, all real drift. Chose merge-base diffing over a committed ratchet baseline because every cleanup PR and hotfix would have to edit that one JSON file across `main`/`test`/`prod`, and a conflicted PR runs no CI at all; renames are followed by `git diff -M`. Promotion and hotfix PRs (`GITHUB_BASE_REF` ≠ `main`) are skipped. Deliberately unrestricted where the DS has no clean replacement (`CircularProgress`, `Collapse`, `Popover`, `Radio`, `List`, `Tabs`, `Autocomplete`); MUI `TextField` is allowed beside MUI `Autocomplete`; `ds/**`, `common/tables/**`, `CustomDropdown`, `CustomDateTimePicker` and shared `navigation/Tabs` are exempt as sanctioned compositions; `// ds-imports-allow: <reason>` is the escape hatch. An unmerged 2026-09 branch (`claude/vercel-agents-content-review-7p8exf`) proposed a warn-only, diff-scoped regex check for hardcoded token values instead; that class stays uncovered here. Counterarguments considered: `main` has no required status checks, so the red `lint` check is advisory until a repo admin adds one — the gate makes drift visible on the PR, it does not block a merge on its own; a PR that sat green while `main` moved is not re-checked. Reconsider if: the allow marker starts appearing routinely (the replacement map is wrong, fix it rather than the call sites), or hardcoded-value drift becomes the bigger regression source (add a separate warn-only check, not a regex in this gate).

- **[2026-09] Token drift joins the same gate, blocking and AST-based, and agents are told at the edit rather than at commit** (`app/scripts/ds-tokens.js`, `app/scripts/check-ds.js`, `.claude/hooks/ds-guard.js`, `.claude/hooks/ds-brief.js`, `.claude/settings.json`, #37432): `check-ds-imports` is renamed `check-ds` and now also fails when a change adds a hardcoded colour, spacing, radius, font size or weight that lands **exactly** on a `--ds-*` scale, including MUI numeric `sx` units (`mt: 2` → 16px → `ds.space[4]`) and the same values passed as JSX props. Token values compare as a multiset against the file's merge-base version, so three `16px` paddings becoming four reports one violation and moving a line reports none. Why this reverses the previous entry's "add a separate warn-only check, not a regex in this gate": both of that entry's premises were about a regex, and this is not one — detection walks the `typescript` AST and only considers property assignments genuinely inside an `sx`/`style` object or a `*Sx`/`*Styles` variable, so `{ color: '#fff' }` in an API payload or a chart config is untouched; and warn-only was a concession to ~264 pre-existing violations, which merge-base diffing already makes irrelevant (the same argument that let the import half block from day one). Exact matching is the load-bearing choice: `#6f6f6f` is `ds.gray[600]`, `#6f6f70` is a deliberate colour and is never flagged, and an off-scale `13px` is left alone — an arguable hit would get the gate switched off. The token table is parsed from `theme-tokens.css` at runtime rather than copied, so §1.8 and the gate cannot drift, and each token's `ds.*` accessor is read out of `src/utils/colors.ts` rather than derived from the variable name — deriving it invents accessors for tokens `ds` does not export (CSS defines `--ds-slate-600`; `ds` has no `slate` key, so the obvious derivation would have answered "use `ds.slate[600]`" and handed someone a `TypeError` at render). A token with no accessor is skipped rather than flagged: the gate can only ask for a replacement it can name, and a test resolves every offered accessor against the real exported object so this cannot regress. Out of scope by design: box dimensions (`design-system.md`'s own Modal recipe uses `minWidth: '140px'`), icon `fontSize` (no icon step exists in the type scale), chart/heatmap files (they need more colour stops than the palette defines), Emotion/styled tagged templates (CSS as text, not an object literal — stated in the module header rather than left to be discovered), and MUI position props — `top`/`left`/`right`/`bottom` go through `positions.js` with no transform, so `top: 2` renders 2px, not 16px, and reading it as spacing would have moved elements 14px. Replaying 700 merges to `main` it flags 52 violations, spot-checked as real, in 4.6s. A `PostToolUse` hook reports the same violations on the file an agent just edited, compared against `HEAD` so pre-existing lines are never attributed to it, and a `SessionStart` hook points at `design-system.md` §1/§1.8/§3 by resolved line number — the doc is ~1,600 lines, so "read design-system.md" gets either skipped or eats a third of a context window. Counterarguments considered: the hooks are Claude Code only, so Gemini (first-class here — `.gemini/config.yaml` runs its PR review) and human contributors are covered by `lint2` alone; per-edit context injection was rejected for once-per-session because a cleanup run touching 42 files would repeat the same block 42 times; a second script duplicating the base resolution and diff walk was rejected for extending the existing one. `design-system.md`'s own `gap='12px'` recipe was corrected in the same PR — the source of truth contradicting the gate is how an agent learns the rule is optional. JSX attribute coverage is the same prop set as `sx`, because MUI's `extendSxProp` folds any `defaultSxConfig` key passed as a bare attribute into `sx` and transforms it identically — an allowlist of nine names let `<Box mt='24px'>` walk past while `sx={{ mt: '24px' }}` was caught. Reconsider if: `// ds-allow` starts appearing routinely (the exclusion list is wrong — fix it rather than the call sites), or the hook's per-edit latency becomes noticeable (it spawns a node process per frontend edit; batch it or move it to `Stop`).

- **[2026-09] services-server splits into API pods and worker pods by a `SERVER_ROLE` env var, gated at one choke point in `common.MqConsume` — not by extracting a second binary or a second chart** (`api-server/services/config/config.go` `ServerRole`/`RunsBackgroundJobs`, `common/mq.go`, `api/ee_registry.go`, `deploy/kubernetes/services-server/templates/deployment-worker.yaml`): every replica used to serve HTTP *and* run all eight RabbitMQ consumers plus the EE startup goroutines, so background load and API latency shared a fate and neither could be scaled without the other. Chose one image with a role flag, defaulting to `all`, over (a) a separate worker binary (`cmd/worker`) — the consumers are registered from package `init()` across eight packages and would all have to be restructured, and two binaries doubles the build/scan/release surface for one deployment concern; (b) per-consumer env toggles — N flags that can contradict each other; (c) a `component` label on the existing Deployment — `spec.selector` is immutable, so an in-place upgrade would be rejected. The split is driven by a single value (`worker.enabled`), which renders the two roles as complements, so no combination of values leaves a queue with no consumer; worker pods get `app.kubernetes.io/name: <name>-worker` so the equality-only Service selector cannot reach them. Counterarguments considered: the gate lives in a transport helper rather than in main (accepted — it is the one place all eight consumers pass through, and a consumer added later is covered without its author knowing the split exists); `MqConsume` returning `nil` when inert looks like success to its callers (mitigated by an explicit log line and by failing *open* — only the exact string `api` disables background jobs, so a typo runs jobs rather than silently draining nothing). Scheduled crons are the largest background workload and are *not* reached by the consumer gate: runbook-server sends 35 triggers to services-server through the main Service, so they always land on an API pod: 34 go to `/rpc-cron`, where 32 of the 35 handler cases run the job as a goroutine on the receiving pod, and one (`Bill Marketplace Buyers`) goes to `/marketplace/billing/charge-buyers`, which runs synchronously in the request. So the chart also renders a `<fullname>-worker` Service, and runbook-server gained `SERVICE_API_SERVER_CRON_URL`, which overrides `{{SERVICE_API_SERVER_URL}}` for cron triggers only and falls back to it when unset — chosen over repointing `SERVICE_API_SERVER_URL` (every other service and runbook-server's own RPC use it) and over a new YAML placeholder (35 edits, and a trigger written later with the old placeholder would silently stay on API pods). The URL is baked into Temporal schedules at runbook-server startup, so enable the worker before setting it and unset it before disabling the worker. The earlier fixes had only a test that hand-built two events; the test added here runs the real rule processor and the real poll builder on one state change, including the rollover second, a delivery that carries an id, and another partition. Rejected for now: an explicit per-firing id field stated by both paths instead of the id derived from fingerprint and start time. It is the cleaner end state, but it changes the id of every alarm row at once, so every open alarm would be stored once more at deploy. Counterarguments accepted: identity is still derived from the event's start time, so a change to what that time means changes identity too (the cross-path test is what would catch it); when both paths check for the firing before either has stored it, the event service's upsert keeps the later delivery and replaces the row's source, title and evidence, a window that existed for the firings that already collapsed and now covers all of them; the row kept outside that window is the first to arrive, normally the push, so code that reads only the poll's source no longer sees the doubled rows it saw by accident. Reconsider if: doubled alarm firings reappear in stored data (count rows that share an alarm and start within two seconds of each other), or the per-firing id becomes an explicit field.
- **[2026-10] A cloud alarm is stored open only where a poll can end it, and the poll is what ends it** (cloud-collector `providers.OngoingSnapshot`, `account/etl_events_ongoing.go`, `providers/aws/cloudwatch_alarm_firing.go`; PROCEED after three REVISE rounds): Every cloud event was sent with an end time equal to its start, which the event service stores closed, so an alarm read as resolved while it was still breaching, had no duration, and restarted its repeat count on every firing. Chose to send an alarm in ALARM with no end time, from the poll and from the push, and to end it from the poll: each poll records every alarm in ALARM (all alarm types, before any is skipped) for the regions it listed to the last page, and the store resolves an open firing in one of those regions when its alarm is no longer listed, or is listed as having begun a later firing. A pushed alarm is stored open only if the account's last poll listed its region and account within the last hour, read from the events job status that poll writes; otherwise it is stored as a moment, as before. Rejected: ending a firing only on a seen transition out of ALARM (an alarm deleted while in ALARM, and an earlier firing of an alarm that cleared and fired again between two polls, would never end); routing the poll's resolve through the event service (its by-finding-id path rewrites priority and labels from the delivery, and its by-fingerprint path is scoped to one source and would also end the current firing); a maximum age for open alarms (an alarm can sit in ALARM for weeks, and without a listing that cannot be told from a stuck row). The resolve writes what the pushed resolve already wrote (`RESOLVED`, `ends_at`, a history row, one resolved notification) through one shared function, and leaves `nb_status` alone, as every source-driven close does; the repeat chain restarts only on a resolved `nb_status` or a gap over the dedup window, so the next firing counts as a repeat. A pushed resolve now ends only firings that started before it, because pushes arrive unordered and more than once. Counterarguments accepted: a firing opened in the hour before an account's polls stop for good stays open until a poll covers it again; a polled firing's end is an upper bound within one poll interval; the job-status write is not awaited, so a failed write makes the next pushes fall back to moments; a firing the poll also catches after a push is still stored twice, which doubles its repeat count until the two deliveries are collapsed (that needs one source for the row, which the alert-tuning and event-rule code read). Consumers that change: the grouping's still-firing arm (`activeRowsWhere`) can now reach an alarm on the same or a dependent subject up to its lookback before the attach window, and the alert-quality statistics see real durations instead of zero-length rows. Reconsider if: open alarm rows accumulate in accounts whose polls fail, or the two deliveries are collapsed (the gate and the resolve then key on one source).
- **[2026-10] A cloud event is linked to its resource once, at ingest, by ranked match — never re-linked afterwards (#41156, PROCEED after REVISE)** (cloud-collector `account/etl_events.go` `chooseEventResource`, `providers.Event.ResourceLookupIds`): One resource id is stored on several inventory rows (an instance's compute row, its management-agent and optimizer rows, cost rows per usage type; a function's row per region), and the linker kept whichever row it read last, so alarms were attached to rows of other services. Chose a ranked choice: the row whose `external_resource_id` equals the event's `service_key`; else a row of the event's own service, id before name; else, only when neither exists, today's id/name match against any service (alarms on custom metrics and events whose service the inventory spells differently have nothing better). Ties inside a tier go to the event's region, then its resource type, then a row read from the provider's API over one derived from the bill; a tie that remains links nothing. Ids the inventory stores differently from the event's subject (a load balancer's ARN against its metric dimension, an ECS service's bare name) are supplied by the provider code that knows them, as `ResourceLookupIds`, not derived in the provider-neutral linker. Rejected: (a) exact-key only, with producers fixed to emit the inventory's key — it unlinks events that are linked correctly today wherever type words or region spellings differ between the two sides; (b) a periodic re-link pass in the collector — it makes a second writer of a column the event service upserts, and the correlation and analysis computed at ingest from the old link would not be recomputed. Accepted: an event stored before its resource is discovered stays unlinked; links made before this change are not repaired. Reconsider if: the event service takes over resource resolution at insert, or the inventory stops storing one resource id on several rows.
- **[2026-10] A cloud alarm firing that cleared between two polls is read from the alarm's history and stored record-only (#41157, PROCEED after REVISE)** (cloud-collector `providers/aws/cloudwatch_alarm_history.go`; event service `PostProcessEvent`, label `nb_record_only`): The alarm poll lists what is in ALARM at that moment, so on accounts with no push feed a firing shorter than the poll interval was never stored. Chose, on every poll and per region, to read the alarm state-change history over a stateless look-back, pair each entry into ALARM with the alarm's next change, and store each cleared firing closed with its real end time under the identity the poll and the push already give a firing (alarm ARN + state-change second), so one already stored is dropped by the existing finding-id check and a firing the same poll still lists is left to the listing. The event carries the label `nb_record_only`; the event service runs triage on it (repeat detection, grouping, alert tuning) and stops before the investigation step and `event.created`, the one point notifications and workflows fan out from. Rejected: (a) a resume watermark for the history read — it has to agree with each region's listing time, which the poll does not record, and re-reading a cleared firing costs one call that the store drops; (b) letting the event service infer "arrived already ended" from `ends_at` — other producers already insert ended intervals and would stop notifying; (c) a gate in each acting consumer — they all hang off `event.created`; (d) priority or `nb_status` as the carrier — priority changes severity and does not stop workflows, `nb_status` is not a producer input. Accepted: the label is visible on the row; it is honoured only for the cloud collector's own alarm sources, so a customer-controlled source cannot use it to mute an alert; a cleared firing is re-read on the next polls inside the look-back; which of two rows of one alarm counts as the repeat follows queue pickup order, as for any two firings close together. An alarm on an expression (metric math, anomaly band) is filed under the first metric of its expression, by the poll and by the push alike. The same rule is to be applied to Azure and GCP firings that are already resolved when read. Reconsider if: a producer outside the cloud collector needs record-only events (then a column, not a label), or the history read becomes a throttling source on accounts with very many flapping alarms.
- **[2026-10] A timing-only incident join is anchored on when the incident began, with a window that depends on how wide the scope is (PROCEED after two REVISE rounds)** (`api-server/services/triage/incident_group.go`: `attachUnlocatedIncident`, `unlocatedScope.window`, `groupLinks.timing`): Chose, for an alert that nothing but the clock connects to an incident, to let it join only when the incident's earliest alert — the head or anything filed under it — started within the scope's window of it, on either side: five minutes when the scope is a whole cloud account, the ordinary fifteen for a namespace or a node. A link made this way places the firing it was written for and nothing else: not a later firing of the same alert, and not another alert on the same subject or a connected one — same-subject evidence does not follow a timing-only placement, so a neighbour of an alert that joined on timing is filed there only if it passes the timing test itself. Over: (a) the previous test, "any member of the group started in the last fifteen minutes", which every joiner renewed; (b) the first draft of this change, which kept fifteen minutes and added two firing-rate conditions (neither the alert nor the incident's head may be a routine one). Why: under (a) one alarm failing every ten minutes kept a group open for hours, the group stayed the only one open, and every unplaced alarm in the account was filed under it, whatever resource it was on; replaying such a timeline through the engine put more than half of its alerts under another resource's incident. Stored timing-only links showed the right ones starting within a few minutes of their incident's earliest alert and the wrong ones spread evenly over the window, so anchoring removes the hours-long groups and a shorter window removes wrong links in proportion. (b) was dropped in review: it is the rate-as-membership gate rejected below ([2026-09]), accounts that re-run one scenario would stop grouping, and the window alone did most of the work. Counterarguments considered: (1) this is a second definition of an "open" incident beside `loadLiveGroups` (another alert's member started inside the window) — accepted and deliberate: a relation through the subject or the service map is evidence that outlives the first minutes, the clock is not, so only this path is anchored and never renewed; one definition for both is a separate decision. (2) The five-minute figure rests on few confirmed links — so it applies only where the scope is widest; for Kubernetes a hand-check of links between five and fifteen minutes found more right than wrong (one alert type failing on sibling workloads minutes apart), so namespace and node scopes keep fifteen, and the wrong links in that band are left for data from after this ships. (3) Anchoring on the first member and leaving the head out, to tolerate an older still-firing cause, was proposed and rejected: in an ordinary group the head is the earliest alert, and leaving it out turns the rule into "five minutes after the first symptom". (4) A later firing of an alert filed on timing used to follow the earlier one through `earlierFiringPlacement` for as long as anything else in the group kept firing; a check keyed on the link reason cannot see that, so the replay asserts composition — no alert under another subject's incident unless the two started together (`cloud_repeating_alarms` in `triage/testdata/grouping_replay`). Not promised: this path joins an existing incident, and only for an alert with nothing related when it is triaged, so several alerts on one new resource form their own group whether or not another incident began beside them. Known cost: an alert that joined another incident on timing no longer groups with a later alert on its own subject, which then stands alone; the replay reports how many. Reconsider if: what is left on cloud accounts is still dominated by a few always-firing alarms (then weigh a rate test again against the scenario re-run case), or the incident model gets one definition of "open".

## What We've Tried and Won't Try Again

- **[2026-10] Using the link's presence as a cluster's on/off state for the agent's own providers** (#40048): Considered having a cluster that reports a signal off delete its link to the shared agent integration row, with the row disabled only once no link was left, so every link-joined reader became per-cluster with no reader changes. Built and rejected in design review because: a user's Disable had no home and could never stick; a one-minute outage deleted and recreated the link row, which carries per-cluster settings; and a provider that was down looked "not configured" to every reader, so nothing could say "configured but unreachable". Current direction: keep configuration, the user's switch and health apart (see the 2026-10 entry above).

- **[2026-10] Automation-run MCP sessions on the relay's per-pod in-memory cache**: considered keying one MCP session per workflow run in the relay's existing in-memory map and closing it with a run-end call (#39634). Rejected because the map is per pod and medium/large installs run 2 relay pods, so step-to-step sharing and run-end closes would silently work only some of the time. Current direction: the shared Redis session directory in [`docs/mcp-sessions.md`](mcp-sessions.md).
- **[2026-09] Multi-account notification rules via an `account_id` mirror beside a scope child table**: Considered keeping `notification_rules.account_id` as a legacy mirror (the single account, or NULL when a rule has several) next to a `notification_rule_accounts` child table, with the matcher falling back to `account_id` when a rule has no child rows. Rejected because: `ON DELETE CASCADE` on the child table removes accounts without updating the mirror, and NULL `account_id` is a wildcard in the matcher, so deleting a rule's last account silently widens it to every account in the tenant; RBAC, the list filter and the batch digest would each read a different representation of the same scope. Also rejected in the same pass: a `match` jsonb with dual-written legacy columns and dropping the source FK, which had no consumer in the slice. - **[2026-09] Breaking the dedup chain when an event's subject changes**: Considered it for incident grouping, where a chain's subject drifts (a CloudWatch alarm repointed from the alarm to its EC2 instance) so grouping keys on a stale subject. Rejected because: subject change is not rare — over 7 days in an anonymized production tenant 22 fingerprints changed subject 2,091 times, and `ecs-task:example-service:family:*` fingerprints change on *every* firing (603 changes across 603 subjects, because the fingerprint is the task family and the subject is the task instance). - **[2026-09] Using the chronic ("routine noise") firing rate as an incident-group membership gate**: Considered allowing routine alerts to join a group but not start one, so noisy alerts stay out of headlines. Rejected because: it makes whether an incident is visible depend on a rate counter versus an arbitrary threshold.
