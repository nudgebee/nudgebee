- **[2026-08] `npm run dev` uses webpack; Turbopack moved to `npm run dev:turbo`**: Chose `next dev --webpack` as the default dev script over staying on `--turbo`. Why: on Next 16.2.12, Turbopack's dev server intermittently fails to match requests that arrive during the cold-boot compile window against pages-router *dynamic* routes — `/api/auth/*` resolves to the HTML `/404` page, which next-auth reports as `CLIENT_FETCH_ERROR: Unexpected token '<', "<!DOCTYPE "...` and makes sign-in impossible. The bad resolution latches for the whole process lifetime and only clears on a filesystem change under `src/pages/`, so restarting does not reliably fix it. Webpack logs `○ Compiling /api/auth/[...nextauth] ...` and serves the same requests correctly (3/3 clean runs vs 2/4 failures on Turbopack, same machine, same race). Cost of the switch: webpack is stricter than Turbopack about `node:`-scheme imports in the browser bundle, so `next.config.js` needs a client-only shim that strips the prefix and stubs `diagnostics_channel` — without it `@prometheus-io/codemirror-promql` (via lru-cache v11) fails the client build with `UnhandledSchemeError` and takes down every page reaching the PromQL editor. `next build` still uses Turbopack, so production was never affected by that. Counterarguments considered: webpack dev is slower on a codebase this size — mitigated by keeping `dev:turbo` for anyone who wants the speed and isn't touching auth; upgrading Next (16.3.1 is released) might also fix it but is a larger change we did not verify. Reconsider if: the repo moves to Next ≥16.3 and the race no longer reproduces — repro is to start the app with the api-server down and a browser already sitting on `/signin`, so `/api/auth/providers` + `/api/auth/session` land during the first compile.
- **[2026-07] Ticket tool services own their wire-format encoding; UIs collect raw values against a closed type vocabulary (#34019)**: Chose server-side encoding at create time (`EncodeJiraAdditionalFields` in ticket-server, fed by the same cached create-meta that drove rendering, wired in `services.CreateIssue`) plus a closed `normalizeJiraFieldType` vocabulary, over (a) frontend-owned encoding (the `customfield_` sniff) or (b) leaving encoding split across both layers. Why: split ownership is what caused #34019 — PR #29541 deleted the backend's priority safety-net assuming a frontend contract only the workflow surface implemented, and go-jira hoists `Unknowns` over typed slots so any raw duplicate silently corrupts the payload. Encoding is deliberately tolerant/idempotent (accepts raw scalars AND legacy `{id:...}` shapes) — that tolerance IS the migration strategy for persisted workflow/autopilot configs and deploy skew; no data migration, no deploy ordering. Counterarguments considered: (1) create gains a meta dependency — mitigated by degrading to hard rules (parent/priority/assignee) when meta is unavailable; (2) unsupported field types (user pickers, cascading selects, sprint) are now dropped from create-meta with logs, so a required one leaves that issue type uncreatable — accepted, it was already uncreatable via silent render-gap deadlock; (3) frontend keeps the `customfield_` `{id}` wrap one more release for old-server skew — remove after ticket-server ships. Reconsider if: a second tool grows Jira-scale custom-field shapes (promote the encode hook from a Jira branch to a `TicketManager` interface method), or prod logs show required-unsupported fields are common (then build real renderers/encoders for them).
- **[2026-04] Templates-as-bare-strings for object-typed workflow params**: Chose permissive `isTemplateString` (contains `{{` or `{%`) bypass in both frontend validators and backend `Schema.Validate` over introducing a `{ $template: "..." }` wrapper object. Why: `ProcessValue`'s simple-variable fast path (templating.go:219-223) and every existing workflow on disk already assume bare-string templates; a wrapper would force a dual-read migration for months. Counterarguments considered: (1) regex heuristic is leaky — literal strings containing `{{` get treated as templates; (2) accepting templates for `integer`/`number`/`boolean` removes the save-time tripwire, shifting type errors to execute time. Reconsider if: we ever need to template *parts* of a map (not just the whole field), or if silent runtime misrenders become a recurring support burden.
- **[2026-05] Single `Optimize` ConversationSource for Optimize-page chats (#29985)**: Chose one canonical `ConversationSource = "Optimize"` plumbed via the existing `source` column, over splitting K8s/Cloud subtypes or filtering on the `recom_` session_id prefix. Why: product wants a single Optimize tab, and `source` (added in migration V452) is the canonical categorization column — session_id-prefix filtering would be data-shape coupling. Counterarguments considered: no backfill (historical chats stay as `UserInvestigation`) and chip-list drift from the Go enum, both accepted as out-of-scope. Reconsider if: product later asks for K8s vs Cloud sub-tabs.
- **[2026-05] ClusterIP→K8sService resolution: defense-in-depth via shared `ResolveIPToK8sService` helper**: Chose two coordinated fixes (source-level short-circuit in traces/ebpf flow sources + new `K8sServiceIPMatchStrategy` enricher backstop) backed by a single canonical helper in `flow_sources/k8s_service_ip_resolver.go`, over enricher-only or source-only fixes. Why: source-level prevents new orphan ExternalService nodes at creation time; backstop catches anything that slips through (future flow sources, stale `req.ExistingNodes`); shared helper owns port-stripping + special-IP skip list + plurality caller-cluster rule so the 3 call sites can't drift. Plurality (most-common cluster, tie→empty→global-unique fallback) chosen over a hard-threshold majority rule to avoid boundary oscillation between builds. Counterarguments considered: (1) interface change to `MatchingStrategy.Match` to pass `extSvc` — rejected, only one strategy needs it; key `CallerClusterIndex` by name instead; (2) DRY across 4 resolution sites including pre-existing newrelic — partial: helper exists, newrelic migration is a follow-up; (3) legacy 672 DB orphan rows survive (SaveNodes upserts, `markInactiveNodes` doesn't touch ExternalService) — user accepted as residual, cleanup deferred to a separate `kg_cleanup_orphan_ip_external_services` RPC action. Reconsider if: pod-IP-named ExternalServices show up at scale (needs a parallel `PodIPResolver`), or if the plurality rule produces wrong resolutions in multi-cluster tenants with skewed traffic.
- **[2026-05] LLM config precedence: DB always beats ENV at any specificity** (llm-server `agents/core/llm_config.go`): Reordered every layered resolver — `ResolveLLMConfig`, `getLLMApiKey`, `getLLMFallbackModelName`, `getLLMApiEndpoint`, `getLLMApiVersion`, `getLLMApiType`, `getLLMRegion`, `resolveLLMSecret` — from the old "specificity wins regardless of source" (env-global → db-global → env-tier → db-tier → env-agent → db-agent) to "ENV block first, DB block on top" (env-global → env-tier → env-agent → db-global → db-tier → db-agent → conversation → context-override). Why: the old order let a stale operator `LLM_PROVIDER_API_KEY_<AGENT>` ENV override silently win over a tenant's canonical DB-global key, fragmenting Google AI CachedContent ownership across calls in one process → 403 PERMISSION_DENIED storms when sibling calls referenced slots owned by a different project. In a multi-tenant product where clients onboard via UI (→ `integration_config_values`), the DB row is authoritative; ENV is operator process default, never a tenant override. Counterarguments considered: (1) operators relying on ENV-agent for emergency overrides now need a DB UPDATE — accepted given the tenant-fragmentation risk; (2) the older "specificity wins" rule was internally consistent and easier to explain — true, but only in ENV-only deployments. Reconsider if: an operator-only emergency override mechanism is needed that bypasses DB without UPDATE access (suggests a dedicated emergency key namespace, not re-elevating ENV-agent).
- **[2026-05] Ticket create-meta: backend-declared field ownership + live-fetch behind Redis (#29541)**: Redesigned the workflow "Create Ticket" field subsystem instead of re-patching. (1) **Ownership contract** — added `FieldInfo.Group` (`severity`/`title`/`description`/`""`) to the `{"data":[Template]}` create-meta payload; the tool builder (which alone knows platform semantics) tags the field backing each basic control, and the frontend renders Platform Fields as `!group` and sources Severity from the `group==='severity'` field. This replaced a hardcoded `key !== 'summary'/'description'/'priority'/'urgency'` filter **plus** a separate `urgency→priority` string alias **plus** a hook skip — three drift-prone encodings of the same fact — with one. Why: a Jira custom field named "Severity" or any synonym slipped the string filter and rendered twice. (2) **Severity flows only via `ticket.Severity`** end-to-end; option `value` is the exact API token each tool consumes (Jira priority **ID**, ZD/PD/SNOW urgency token), and the hook stops preferring `id` — fixing "loads ≠ applies" (ZenDuty silently defaulted to Medium; PagerDuty create ignored urgency entirely). Jira create sets `Priority{ID}` once (removed the `additionalFields["priority"]` double-write); runbook `tickets.create` migrates legacy `additional_fields.priority/urgency` → severity. (3) **Reliability** — Jira severity/assignee fetch live (`Priority.GetList` + first-page assignable users) and seed/synthesize, so they populate even when createmeta omits allowedValues or GDPR-strict blocks user search; **no dependency on the `integration_config_values` snapshot** (product decision). PagerDuty gained an urgency field + create wiring; ServiceNow `GetCreateMeta` implemented (urgency + live `sys_user` assignee, no labels). (4) **Caching** — `services/cache` (eko/gocache redis+bigcache mirror of api-server, separate module so can't import) wraps the unified registry seam `fetchCreateMetaCached`, 30-min TTL, graceful degradation (Redis down ⇒ live), invalidated by integration tag inside `updateMetadataConfigValues` (covers save/test/bi-hourly sync). Redis comes free via the shared `nudgebee` secret (`CACHE_PROVIDER=redis`) — no k8s change. Counterarguments considered: (1) extra live Jira calls per cache miss — bounded (one priority call + first-page users, only on 30-min miss); (2) snapshot-only with no Redis would also fix the matrix since #29541 is a correctness not latency bug — Redis kept per product decision. Reconsider if: create-meta latency was never the real pain (then drop Redis for snapshot-warm), or pod-scale Jira user lists need server-side search instead of first-page seeding.
- **[2026-06] Webhook auth model — edge verifies provider identity, notifications gates on an internal token**: Inbound chat webhooks are authenticated at the Next.js edge (`app/src/pages/api/webhooks/*`): Slack by HMAC signature (signing secret required; reject missing headers; 5-min replay window), Google Chat and MS Teams by provider JWT (Google certs / Bot Framework `login.botframework.com`, audience = app id; MS Teams adds a `serviceurl`-claim match + 5-min clock tolerance). The edge forwards to `notifications-server` stamping `X-ACTION-TOKEN`; every notifications `/webhooks/*` endpoint requires that token (constant-time check in `notifications_server/security/webhook_auth.py`). `/webhooks/slack/events` is also routed directly to notifications by the app ingress, so that endpoint additionally accepts a Slack HMAC over the raw body (`slack_sdk.SignatureVerifier`, reading `settings.slack.signing_secret` — not the placeholder-defaulting `slack_app` secret). MS Teams uses a Bot Framework Bearer JWT, not an `x-ms-signature` body HMAC (see the entry below). Every check requires its secret/token to be configured. Reconsider if: the direct `/webhooks/slack/events` ingress route is removed (Slack verification then lives only at the edge). Follow-ups: a dedicated `EDGE_TO_NOTIFICATIONS_TOKEN` instead of reusing `ACTION_API_SERVER_TOKEN`; `bodyParser:false` + raw-body read on the Slack edge handlers (they currently recompute the HMAC base string from a re-serialized body). Ops note: `ACTION_API_SERVER_TOKEN` must be pinned (explicit value or `existingSecretName`) so the edge and notifications share one value — a GitOps lookup-or-generate can otherwise regenerate it per reconcile, after which edge-forwarded webhooks stop being accepted.
- **[2026-06] GitHub App install carries identity in OAuth `state`, not the session cookie**: Added `app/src/pages/api/integrations/github/install.ts` — the modal now opens this same-origin endpoint (session cookie present), which `encrypt()`s a minimal JWT identity (`id`/`tenant_id`/`roles`/super-admin flags + `ts`, AES-256-GCM, 10-min TTL) into the GitHub installation `state`; the callback recovers identity from `state` and only falls back to the cookie. Why: GitHub was the lone integration whose callback depended on the NextAuth cookie surviving GitHub's cross-site redirect into a popup (third-party-cookie partitioning / SameSite / host drift drop it → recurring `not_authenticated`, 4 prior patches that all kept the cookie dependency). This is the Slack/Google pattern (identity via `state`, cookie-free callback). Counterarguments considered: (1) depends on the App having "Request user authorization (OAuth) during installation" enabled for `state` to round-trip — but the existing `redirect_uri`→`installation_id` behavior implies it's on, and the cookie fallback means no regression if not; (2) identity in a URL param — mitigated by authenticated encryption + TTL, strictly better than the unbounded cookie. Reconsider if: GitHub stops echoing `state` on the install flow (then move to a server-stored nonce).
- **[2026-06] Agent PR-followup dispatch: coalescing `pr_followup_pending` flag + atomic claim-or-mark / finalize-and-clear, dispatcher stays content-agnostic** (`api-server/services/account/adapter/pr_lifecycle.go`): A webhook signal (review/comment/CI failure) landing while a followup is in flight (`pr_lifecycle_state='addressing'`) used to lose the claim race and be silently dropped, recovered only by the cron after a 60-min cooldown as a generic run. Chose a single boolean `pr_followup_pending` (migration V750, both `event_resolution` + `recommendation_resolution`) set by an atomic claim-or-mark and read-and-cleared by an atomic finalize, with one bounded re-dispatch on completion. Both sides are single row-locked statements (`FOR UPDATE` CTE) so they linearize: either the mark commits first (finalize sees pending → re-dispatch) or the finalize commits first (the concurrent dispatch then claims directly) — no interleaving loses the signal or orphans the flag. A single boolean (not a queue) intentionally coalesces N concurrent signals into one re-run; the agent's `no_op` is the sole arbiter of relevance — **no comment content/source heuristics in dispatch** (rejected hardcoding labeler/bot markers as overfit to our env; customers' noise differs). Also retire resolutions on `pull_request closed`/merged (terminal state, skip the run; finalize preserves terminal so a mid-run close isn't resurrected). Counterarguments considered (via `/challenge`): (1) optimizes dispatch precision while the workspace `gh`/`GH_TOKEN` auth is still broken so followups can't yet succeed — accepted, the dispatch fix is correct independent of auth; (2) re-dispatch removes the cooldown's implicit rate/cost control — mitigated by coalescing + `no_op` not bumping the iteration cap + a `maxRedispatchChain` budget; (3) hand-rolled queue-in-a-table doubles the state space — accepted for near-real-time recovery vs the self-healing-but-60-min cron. Reconsider if: re-dispatch run-rate becomes a cost problem at scale (move to a real queue), or the cron backstop alone proves sufficient once auth works.
- **[2026-06] Slack/MS Teams → `integrations` table with tokens encrypted at rest (storage migration, OAuth flow unchanged)**: Moved Slack/MS Teams off the legacy `messaging_platforms` table into `integrations`/`integration_config_values`, with OAuth bot/access/refresh tokens encrypted (`is_encrypted` + `common.Encrypt`; new `slack.go`/`ms_teams.go` types mark those fields `IsEncrypted`). Chose **Option A — notifications-server holds the shared `NUDGEBEE_ENCRYPTION_KEY`** (byte-compatible Python AES-256-GCM port in `notifications_server/security/secrets.py`, locked by a Go-produced fixed-nonce KAT) so it encrypts on OAuth-install/Teams-refresh and decrypts on the send hot path locally — no new hot-path round-trips, OAuth flow untouched. Channels are stored as a **scalar `default_channel_id`** (+ `default_team_id` for Teams); only IDs drive sending (display names cached, not authoritative). **One install per tenant is code-enforced** (upsert-by-`(tenant,type)`), not a DB constraint. Every read unions legacy + integration via `services/messaging_installations.py` (integration wins, dedup by `(tenant,platform)`), so the migration is transparent before backfill. Backfill is an idempotent **operator-run internal endpoint** (`POST /v1/integration/messaging/backfill`, X-ACTION-TOKEN) — not a gateway action, since cross-tenant ops stay server-side (see the `admin_*` note in [`rpc-action-naming.md`](rpc-action-naming.md)). Counterarguments considered: (1) the shared key widens a notif-server compromise to all integration secrets (Jira/PagerDuty/DB) — accepted as strictly better than today's plaintext tokens, and the OAuth/refresh logic already lives there; tighten to api-server-owned crypto if posture demands; (2) the secret-field set is duplicated (Go `IsEncrypted` vs notif-server `_SECRET_FIELDS`) — kept to one obvious constant per side; (3) a long-lived dual store until backfill runs — bounded by the integration-wins dedup. Reconsider if: the key blast-radius becomes unacceptable (move to api-server-owned encrypt/decrypt via a scoped internal endpoint + in-memory token cache), or we ever need >1 messaging install per tenant (revisit the dedup rule + add DB-level uniqueness).
- **[2026-06] FinOps score v1 — explicit cross-category exchange rate; selection diversity lives in queries, not the score** (`api-server/services/recommendation/finops_score.go`, #32118): Replaced the v0 blend (40% universal severity+recency / 60% category-specific) with flat per-category weights — security 1.0·sev, performance 0.90·sev, config 0.70·sev, cost 0.80·log-savings ($5K ceiling) + 0.20·sev — making the cross-category exchange rate explicit and tunable (Critical config 70 ≈ a $600/mo cost rec, High config 53 ≈ $100/mo); cost recs with savings ≤ 0 score as performance (they are "increase resources" reliability recs); recency is a small additive boost (+8/+5/+2) instead of 16–34% of the score. Why: the v0 linear /$500 savings curve zeroed the typical rec (live p50 savings = $1.9/mo), so the finops top-100 was 100% config findings with $0 savings, and the recency weight kept the list equal to "today's scan output". Scanner upserts no longer overwrite finops_* on conflict (the k8s path scored recency from now(), scan_orchestrator wrote literal 0) — the 6h recompute cron owns refresh for existing rows. Counterargument that shaped the design: simulation on live data showed **no scalar score fixes the list alone** — any >100-row same-score cohort (4,187 High config, 321 Critical $0-savings rightsizing) floods a top-N — so curation = score **plus** per-rule-family ROW_NUMBER caps in the nudge/digest selection queries. Reconsider if: band-driven nudge/digest volume shifts badly after recalibration (band thresholds kept at 90/75/55/35), or per-tenant savings scales make the fixed $5K log ceiling wrong (then percentile-normalize savings within tenant).
- **[2026-06] Per-source webhook subject/namespace mapping = per-integration override layer on the existing tenant label-mapping mechanism, not a new DSL** (`api-server/services/integrations/core/integration_webhook.go`, #30987): The headline gap for the Flipkart PoC was that `webhook_label_mapping` (subject/namespace/severity → ordered label key specs: plain key, `key|regex`, or gonja template) existed only **tenant-wide**. Chose to make it **per-integration** by auto-injecting a hidden `webhook_label_mapping` config value on every `IncidentWebhook` integration (mirroring `account_mapping`) and applying it as an **override** layer ahead of the tenant-wide **fill-empty** layer (`applyConfiguredLabelMappings`), reusing the exact same key-spec syntax, compiled cache, and `extractLabelValue` — over (a) a new JSONPath/DSL over the raw payload, or (b) a second parallel mechanism. Why: Flipkart's two example fields are **already label-reachable** (Prometheus flattens `labels.fk.service`; ZenDuty exposes `incident.service.name` as label `nb_zenduty_service_name`), so no raw-payload access is needed; one syntax / one apply path avoids drift (the repo's standing concern). Override (not fill-empty) for the per-source layer because an admin who declares "service-name comes from X" means it authoritatively — but a spec that **misses** on a given alert never clobbers the parser's value, and default-empty config means zero regression for existing tenants. Scope: backend + integration-config API only (no UI); covers subject+namespace+severity. Counterarguments considered (via `/challenge`, verdict PROCEED): (1) override before workload-validation lets a typo'd rule set a non-existent subject and **suppress the LLM fallback** — accepted as the intended "no LLM fallback when explicitly mapped" behavior; `MatchWorkloadAndEnrich` still stamps `nb_matched_workload=false` as the visibility hook; (2) reusing the `webhook_label_mapping` name at two storage scopes (tenant_attr vs integration_config_values) — intentional, same concept different scope, documented on `WebhookLabelMapping`. Reconsider if: a customer needs a field that is **not** label-reachable (then add a raw-payload `payload.*` context to `extractLabelValue`, not a second mechanism), or the deferred #30987 reqs 3–4 (LLM "suggest a rule" learning signal + unparsed-alert visibility surface) are picked up.
- **[2026-06] Series-match metric discovery: new `metrics_list_series` action + optional `MetricSeriesSource` capability, per-candidate `label/__name__/values` probe, per-family label grouping** (`api-server/services/observability/prometheus_series.go`, #32406): To stop the AI assistant reporting "N/A" for a service's metrics when its instrumentation differs from the default template, added a deterministic primitive: given `(provider, namespace, workload)` return the metric `__name__` families that actually have series. Chose a **new action** over extending `metrics_list_names` (different contract — label selector vs substring — and cache key) and an **optional `MetricSeriesSource` interface** the orchestrator type-asserts over adding a 7th method to `MetricSource` (only Prometheus/VM implement it today; ES is a follow-up; other providers return a clear "not supported" instead of forced stubs). Discovery probes a **set of candidate `(namespace-label, workload-label)` pairs** — one **`/api/v1/label/__name__/values?match[]=<selector>` lookup per candidate, dispatched concurrently** (bounded) — and **groups returned families by the labels that found them**, because a workload commonly emits under several layers at once (validated live on `llm-server`: eBPF `container_http_*`/`container_net_*` under `destination_workload_name` **and** scraped `http_server_*`/`nb_llm_*`/`go_*` under `job`/`pod`), and querying an eBPF family with `pod=` (or vice-versa) returns empty — so a flat family list + single workload label would reproduce the N/A bug one layer down. **Critically, discovery asks the engine for the distinct `__name__` VALUES, not for series.** The first cut issued ONE `/api/v1/series` call with all candidate `match[]` and capped on **series count** — but a single high-cardinality family (cAdvisor `container_*`) collapses to one `__name__` yet explodes into thousands of series, so it exhausted the shared series budget before a workload's low-cardinality families were returned, reproducing the very N/A bug one layer down (verified live: **zero `nb_llm_*` families even at the max `limit` of 5000, result always truncated**). Querying families sidesteps cardinality crowding by construction and reads the label index instead of materialising series (measured on VM: **~0.9s/lookup, flat across 5m–24h windows, vs 8–11s for the series call**; 12 candidates concurrent ≈ 1s); `limit` now caps **families per candidate** (catalog-sized → default 500, max 2000, essentially never trips); per-candidate failures are isolated (one flaky lookup can't discard the others — only an all-candidates failure errors). **No metric family name is hardcoded anywhere** (families are read back from the engine; only the small, stable namespace/workload *identifying-label* convention set is declared, in an overridable package var); `pod` matches by an anchored prefix regex (replica-hash suffix; server-side regex == client-side `HasPrefix`), others exact. Counterarguments considered (via `/challenge`): (1) N concurrent calls vs the original "single call" — **refuted by measurement**: label-values is ~10× cheaper than materialising 5000 series and concurrent dispatch finishes faster than the one series call it replaces, so "bounded + cheap" is *better* served, not worse; (2) per-candidate lookup reintroduces an unbounded scan (the expensive path the issue warns about) — **refuted**: latency is flat across lookback windows and result size is metric-catalog-bounded, not series-bounded; (3) filter cAdvisor/`container_*` noise by name — **rejected** as a hardcoded scenario that overfits one cluster (the fix must stay general — label-values makes the noise harmless without naming it); (4) a candidate *label* list is still a form of hardcoding — accepted because identifying labels are a far smaller/stabler space than family names, the var is overridable, and unknown labels only cost coverage not correctness; (5) extend `metrics_list_names` instead — rejected for contract/cache clarity. Reconsider if: candidate labels need per-tenant config (wire the package var to viper/env — currently a noted follow-up), `label/__name__/values` + `match[]` proves too costly on a very-large-cardinality tenant at scale (re-add a defensive cap / shorter lookback), or pod-IP/own-metrics conventions appear that the fixed candidate set misses. Follow-ups (PR-2, the consumer change): gateway `actions.yaml` registration (deferred here since nothing calls it through the gateway yet — the llm-server hits `/rpc/metrics` directly with `X-ACTION-TOKEN`); ES `FetchMetricSeries`; llm-server `metrics_series_match` tool + prometheus-agent empty-result wiring gated behind `LLM_SERVER_RCA_MATURITY_ENABLED` (depends on the RCA-maturity work landing).
- **[2026-06] llm-server outbound egress filter — single `Filter` interface, build-tag-gated EE bundle, generic `metadata jsonb` for per-message events** (`llm/llm-server/security/egressfilter/`, PR #30033): New per-LLM-call gate in `agents/core/llm_config.go::GetLLMModel`, off by default (`LLM_SERVER_EGRESSFILTER_ENABLED=false`). Three coordinated decisions: (1) **One `Filter` interface** (`Detect(payload) []Hit`) with `Register(name, Filter)` + `RegexFilter` / `FilterFunc` adapters — over a separate RuleRegister / EntropyRegister pair. Why: entropy is just another detector; symmetric API removes a dual-path the regex pass and the entropy pass already had. (2) **Build-tag-gated EE bundle** (`cmd/imports_enterprise.go` behind `//go:build enterprise`; `Makefile` uses generic `BUILD_TAGS` variable) over inline blank-imports in `main.go`. Why: `main.go` carries zero EE path references, so the OSS-sync filename rule (`*_enterprise.go`) drops EE wiring cleanly with no line-edits. OSS baseline ships 5 unambiguous rules (`aws-access-key-id`, `private-key-header`, `github-pat`, `openai-api-key`, `anthropic-api-key`); EE adds 12 + Shannon-entropy gate. (3) **Generic `metadata jsonb` column on `llm_conversation_messages`** (migration V761) merged via PG `||` operator + namespace-keyed payloads (`metadata.egressfilter`, future `metadata.pii_tokenization`) over a dedicated `llm_egressfilter_events` table. Why: per-message subsystems each own one top-level key, shallow JSONB merge survives sibling writes from independent subsystems (Piyush's #31273+#31514 PII track lands its own key), UI does one read per message. The wrapper emits one `FilterEvent` per outbound LLM call with `Hits []Hit` (each carrying `Start/End`/`Placeholder` for the future redact mode) via a `WithFilterEventReporter(ctx, fn)` context callback. Atomic-value-backed registry → lock-free, allocation-free hot path (verified 0 allocs/op on clean Scan). Counterarguments considered: (1) redundant with the per-alert verdict's `blast` dimension — resolved by making criticality a stable per-workload input the verdict *consumes* (grounding), not a second scorer; (2) LLM non-determinism (critical count wobbled 4–7 run-to-run) — mitigated by sticky `user` overrides the nightly re-derive never touches. Reconsider if: a workload class needs promotion the topology heuristic can't recall at acceptable latency (revisit all-workloads with class-dedup + a "medium is default" prompt), or scoring needs criticality to *force* the band rather than advise it.

- **[2026-07] NB AI Gateway P1 — standalone `llm/gateway/` module, Bifrost HTTP sidecar for passthrough, NB-owned control plane** (`llm/gateway/`, `nudgebee/llm-gateway`): New everyone-facing gateway (any org tool → NB token → provider). - **[2026-07] Account-scoped custom roles: scope lives on the GRANT (role×module), not the assignment — built phased, foundation-first** (`api-server/migrations/…_V798_scope_custom_role_permissions`, `api-server/services/security/security_context.go` `NewSecurityContext`): The RBAC-v1 entry above flagged "entity-scoped custom roles" as a future reconsideration; on `feat/dynamic-rbac` the half-wired state (V797 added `entity_type`/`entity_id` to `custom_role_assignments`, plus `scopedCustomPermissions`/`HasScopedPermission`/`CanReadAccountData`, but **no write-path**, and the gateway + query-engine gates are tenant-global-only) meant the account tier was unreachable and the UI's `account` scope heading advertised per-account scoping the system couldn't enforce. Chose to put scope on the **grant** (`custom_role_permissions.entity_type/entity_id`, V798) over the **assignment** (V797) so a single role can hold tenant-config modules tenant-wide **and** operational modules per-account coherently — over scope-on-assignment (forces splitting a role per account, can't mix tenant + account modules) and over deferring the model choice. Built **phased**, enforcement never ahead of the grant surface (`/challenge` verdict REVISE): **Phase 1 (done)** = V798 scope columns (NULL = tenant-global; re-keyed the unique index to include scope) + switched `NewSecurityContext` to read scope from the grant (`crp`) instead of the assignment (`cra`) — a proven **no-op today** (every existing grant row is NULL-scope → identical tenant-global output), but the read-path is in place **before** any scoped row can exist, so a later writer can't silently leak by being read tenant-globally. **Phase 2 (backend done)** — the re-challenge (verdict REVISE) replaced the hand-maintained "account-scopable module whitelist" with a **route-derived** rule: a scoped grant is honorable only for a module that owns a `/rpc/query` `PermissionModule` table with a per-account column, computed by `query.AccountScopableModules()` (PermissionModule + AccountIdColumnName) so the write-time guard can never drift from enforcement. Shipped: (a) grant-level `EntityType`/`EntityId` on the write-path (create/update persist, get/list return, `validatePermissions` rejects an account-scoped grant on a non-scopable module or malformed scope); (b) query-engine enforcement — `service.go` grows a scoped-grant branch that restricts a scoped caller's read to `AccountIdColumnName IN ScopedAccountIdsForModule(module)`, mirroring the built-in account-role branch (aggregates scope to the granted accounts; empty → no rows, fail-closed). Still inert end-to-end because the gateway/session only admit tenant-global grants — no leak. **Phase 3 (done — the keystone; inline `/challenge` verdict PROCEED)** = scope-aware session/gateway admission. Scoped grant keys are baked into the session as `scoped:<module>:<Class>` (a prefix on the existing `permissions` array — chosen over a new `scoped_permissions` field so it rides the fully-wired session path end-to-end: no NextAuth/UserService/SessionVariables changes, and both session-build sites carry it for free). The gateway (`actionHasCustomGrant`, extracted pure + unit-tested) honors a scoped key ONLY when `route.handler` ends in `/rpc/query` — the one uniformly per-account-gateable path — so custom-handler actions stay tenant-global-only and fail closed for scoped users. `ListUserPermissions` appends the prefixed scoped union (`GetScopedPermissionKeys`). **Phase 4 (done)** = role-editor scope UI — the editor loads active accounts and, for each granted account-scopable module, offers an optional account multi-select ("All accounts" default); `handleSave` emits one scoped grant row per selected account (`entity_type='account'`), and edit hydrates scope from the role's permission rows. Consumers (llm-server + runbook-server `scPub`) already carry `ScopedCustomPermissions` + `HasScopedPermission`, so the cross-`SecurityContext` wire needed no change. V797's assignment-scope columns are superseded by V798 (left in place, unused; drop is a later cleanup). Counterarguments considered (`/challenge`): (1) a flat gateway union of scoped keys leaks tenant-wide on no-downstream-gate handlers — avoided by deferring enforcement to Phase 3's scope-aware shape; (2) "extract the target account" has no total definition (cross-account aggregates carry no account) — Phase 3 gates the skip on a concrete account filter only; (3) mixed-scope role coherence — resolved by scope-on-grant. Reconsider if: scope-on-grant's "same role → same account for every assignee" proves too rigid (then move scope back onto the assignment, or add a per-assignment override layer), or the account-scopable catalog can't be kept faithful to the downstream gates (generalize a per-table "account-enforced" flag + shared allowlist). See [[project_rbac_query_engine_permissionmodule]], [[project_security_context_contract]].

- **[2026-07] Dynamic RBAC is a per-tenant feature switch, not a build-time one — one gate (`security.CustomRolesEnabled`) that collapses every custom-role gate back to the built-in roles** (`api-server/services/security/custom_roles_feature.go`, the `custom_roles_feature_flag` migration, `app/src/lib/auth.tsx` `isCustomRolesEnabled`/`isGrantsOnlyUser`): The feature previously had no runtime off switch — only OSS build-stripping of `app/src/ee/` + `services/ee/`, which removes the *management* surface while the *enforcement* path (the `NewSecurityContext` grant resolver, `CanManage`, `CanReadAccountData`, the query-engine `PermissionModule` skip, the gateway grant check, and the frontend grants-only UI gating) stays compiled and live. Two consequences drove this change: the resolver queried `custom_role_*` unconditionally, so a services-server rolling out ahead of its migration Job failed **every** authenticated request; and there was no way to turn the feature off for a tenant once on. Chose a **per-tenant `CUSTOM_ROLES` feature flag** in the existing `public.feature`/`feature_flag` tables (same mechanism as `MEMORY_MODULE`/V717, registered but not enabled by that migration — opt-in per tenant), plus a deployment-level `CUSTOM_ROLES_DISABLED=true` env kill switch that beats it, over (a) a build tag (can't be flipped per tenant or without a redeploy), (b) a license-tier gate (tier is about entitlement, not rollout state), (c) leaving the OSS strip as the only seam. The design rests on one property: **every** backend custom-grant gate funnels through `HasPermission`/`HasScopedPermission`, so leaving both grant maps empty reduces `CanManage`→`IsTenantAdmin()`, `CanReadAccountData`→`HasAccountAccess(read)`, `ScopedAccountIdsForModule`→nil and the session grant list→`[]` — authorization becomes bit-for-bit the built-in-role behavior, and the tables are never touched. So the switch is applied at exactly one backend point (skip the resolver in `NewSecurityContext`), and the flag state rides to the browser on the session (`customRolesEnabled`, from `customroles_list_user_permissions`) so the frontend gating layer has the same single switch: `isGrantsOnlyUser()` returns false when off, which is what makes the disabled nav icons / cluster tabs / quick links / Troubleshoot sub-tabs disappear (it also replaced five copy-pasted `!isTenantWideRole() && getSessionAccountIds().length === 0` computations). `hasPermission`/`canManage`/`hasAdminSurfaceAccess`/`hasAnyCustomGrant` all re-check the switch so a JWT minted while the feature was on cannot keep gating after it is turned off. Custom-role CRUD is refused while the flag is off (`guardCustomRolesEnabled`) so an admin cannot build grants the resolver ignores; `customroles_list_user_permissions` is deliberately NOT gated, since it is how the session learns the switch state. Two staleness fixes were required for the switch to be real rather than nominal: the JWT's grant set is now re-resolved on session rotation at most every 5 minutes (`PERMISSIONS_REFRESH_MS`) instead of being frozen at login — otherwise a revoked grant, or the feature being turned off, kept working for the life of a signed-in session; and `UpsertFeatureFlags` drops the tenant's security-context cache when the written flag is `CUSTOM_ROLES`, since that flag is read while *building* a context and contexts live 30 minutes. Counterarguments considered: (1) an extra flag query per security-context build — it only runs on a cache miss, and when the feature is off it *replaces* a 3-table join, so the off path is cheaper than before; (2) two switches (flag + env) are two things to check — accepted deliberately, because the env one must work when the database or the flag rows are themselves the problem; (3) the flag could have been read inside `HasPermission` for instant effect — rejected, that is a per-check DB read on the hottest authz path, and cache invalidation on flag write gets the same result. **Correction to the entry above:** the scope model is now scope-on-**assignment** (`custom_role_assignments.entity_type/entity_id`) — the `scope_custom_role_permissions` migration drops the grant-level scope columns and `NewSecurityContext` reads `cra`, so the "scope lives on the GRANT" entry describes a superseded state. Reconsider if: the flag needs account-level granularity (the `feature_flag` row already supports `account_id`), or tenants want the feature on by default (switch the reader to `IsFeatureEnabledByDefault` semantics — but then "off" needs an explicit disabled row everywhere).

- **[2026-06] `x-ms-signature` HMAC for the MS Teams webhook** (`app/src/pages/api/webhooks/msteams/events.ts`): MS Teams (Azure Bot Service) authenticates inbound activities with a **Bearer JWT** validated against Microsoft's OpenID metadata (issuer `https://api.botframework.com`, audience = app id) — **not** an `x-ms-signature` body HMAC keyed by the OAuth client secret. - **[2026-07] Deriving custom-role account scope from the assignee's built-in account role** (`api-server/services/query/service.go` `hasModuleGrant`): Considered making a tenant-global custom grant stop bypassing the account-restriction block whenever the caller holds a built-in account/namespace role — so "Group A → account_admin on Account A + custom Role A" would scope Role A's permissions to Account A, letting the "Restrict to accounts" picker be removed from the role editor in favour of the existing group→role→account binding. Rejected because: the data-scope carrier is a **broad** role — the narrowest built-in account role grants 250 of 442 actions (`account_admin_readonly`; `account_admin` grants 355) — so an admin wanting "Events Viewer on Account A" would first have to hand over 57% of the action surface, inverting least privilege into escalation. Two further defects: routing namespace admins back into the restriction block fires `updateQueryWithNamespace` on tables with no `NamespaceColumnName` (e.g. `get_cloud_accounts_v2`), breaking the account/cluster picker for that persona; and the same custom role would resolve to a different data scope per assignee depending on unrelated built-in roles, so adding an account role would silently *narrow* a user's custom-grant data and "who can see Account B's events" would require joining grants against every user's role assignments. Current direction: keep V798 scope-on-grant as the enforcement substrate and close the real gap — per-account enforcement exists only on `/rpc/query` (25 of 80 actions across the 7 account-scopable modules; `events` alone has 22 of 28 denied). Wire `HasScopedPermission`/`CanReadAccountData` into custom handlers module by module (start with `events`); only once a scoped grant delivers a whole module does moving scope from the grant to the group assignment become a pure UX choice.

Why: GCP notification channels aren't in inventory, inventory is hours-stale for a picker, and one uniform live path beats per-provider inventory-meta parsing; listing needs no new IAM (ReadOnlyAccess / Viewer / Reader already cover it).
