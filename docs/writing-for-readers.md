# Writing PRs and issues people actually read

> Applies to every PR description, issue, and review comment this repo produces — written by a
> human or generated by an agent. Skills that must follow it: `/create-pr`, `/create-issue`,
> `/ship`, `/review-pr`, `/pr-comments`, `/code-review`.

## The rule

**Uncompressed text is work you moved onto the reader.**

Whoever produces the words is the one who compresses them. That is the same instruction to both
readers of this file:

- **If you are an agent drafting a PR body, issue, or review comment** — the draft is not the
  deliverable. Fluent, correct, well-organised prose is your *cheapest* output, not your best one;
  900 words of it costs you nothing and costs every reviewer ten minutes. Compressing it is not a
  polish step after the writing, it *is* the writing. Do not hand a human a draft to trim.
- **If you are a person about to paste a model's output** — you are the last one who can compress
  it before it reaches the reader. Cut it to what you would have written yourself, or send three
  sentences and a link.

Either way the failure is the same: shipping the first draft is not thoroughness, it is delegating
the editing to whoever opens the PR.

## Structure: one screen, then a fold

Every PR body and issue has the same shape. Order is not negotiable; sections are.

1. **Lead — 3 sentences, no jargon.** What changed, who it affects, why it mattered.
2. **How to verify — reader-side steps.** What *someone else* does to confirm it works.
3. **Risks — max 3 bullets.** Only things a reviewer should actively evaluate. Omit if none.
4. **`<details>` fold — everything else.** No length limit. This is where the depth lives.

**Budget: everything above the fold fits one screen — hard cap 200 words.** The fold is unlimited,
so nothing is ever lost by respecting the cap; detail is *demoted*, not deleted.

```markdown
<details>
<summary>Engineering detail — root cause, measurements, what's not in this PR</summary>

...anything you want, at any length...

</details>
```

## Author-side evidence is not reader-side verification

The single most common miss. These are different sections with different audiences:

| | Belongs |
|---|---|
| "`go test ./agents/core/` — green, `golangci-lint` — 0 issues" | **Evidence.** Inside the fold. Proves nothing broke. |
| "Open Settings → LLM, run any investigation on a Bedrock account. Responses should no longer stop mid-sentence." | **Verification.** Above the fold. Lets a reviewer or QA confirm the claim. |

**If your "How to verify" contains only commands you ran, you have not written it yet.**

Write it for a tester who will not open the codebase: where to click, what to type, what they should
see, and what they'd have seen before the fix. If the change has genuinely no observable surface
(background job, silent data drift, internal refactor), say exactly that in one line and put the
developer-level probe — SQL, `kubectl`, log query — in the fold. One honest line beats a fabricated
UI flow.

## Never above the fold

Function, method, struct or column names · `file.go:513` · commit SHAs · migration ids · library
versions · stack traces · SQL · per-file change tables · anything a non-engineer would have to
look up.

Naming a service (`llm-server`, `relay-server`) is fine. Naming a symbol inside it is not.

## Delete on sight

- **Per-file / per-function change tables.** GitHub renders the diff directly above your text. A
  table restating it is machine output pasted back at the reader.
- **`Impact: None` · `Performance: Negligible` · `N/A`.** An empty section is worse than an absent
  one. Delete the heading.
- **Sentences that restate their own heading.** ("## Risks — There are some risks with this change.")
- **Summaries of the summary.** One lead, one time.
- **Hedging that survives to the reader.** Either you verified it or you didn't — say which.

## Numbers, not adjectives

"Significantly slower" is unreviewable. "30% of calls (17/57) hit the cap, costing ~20 min of a
41-minute investigation" is a fact someone can argue with. Put **one** number in the lead; put the
table in the fold.

## Four tests before you post

Re-read your own draft and answer these. Any failure is a rewrite, not a caveat.

1. **Skim test** — reading only the first three lines, can a PM tell what changed and whether it's
   risky?
2. **Jargon test** — is there a symbol, path, SHA, version, or error string above the fold?
3. **Reproduce test** — could QA follow "How to verify" without opening the codebase?
4. **Slop test** — delete every sentence that restates the diff, hedges, or exists to look
   thorough. Did the meaning survive? Then it should have been deleted.

## Worked example

**Before** — 840 words, opens on a symbol name, testing section is a list of commands the author ran:

> `GetLlmMaxOutputTokens` matched Claude only up to `claude-3` and OpenAI only up to `gpt-4o`. Every
> newer model fell through to `return 0`, and the caller (`llm_common.go:513`) turns 0 into a
> hardcoded 4096 — about 3% of the 128k these models actually support. […5 tables, 6 subsections…]
>
> **How Has This Been Tested?** `go test ./agents/core/` — green. `golangci-lint run` — 0 issues.

**After** — 110 words above the fold, same information, nothing lost:

> Investigations on newer models (Claude 4.x/5, GPT-5, o-series) were being cut off at 3% of the
> output length those models support, then silently stitched back together from up to 4 retries.
> Nothing errored, so it never surfaced as a bug — one customer investigation spent **~20 of its 41
> minutes** on those retries. This raises the ceilings and logs a warning whenever a model still
> falls back to the old default.
>
> **How to verify**
> 1. Run any investigation on a Bedrock account (`us.anthropic.claude-sonnet-4-6`).
> 2. Watch `llm-server` logs — `Attempting continuation` should be rare, not 35× per investigation.
> 3. Responses should read as one answer, not restart mid-sentence.
>
> **Risks** — self-hosted models (Qwen, llama, mistral) deliberately stay on the old default; their
> real ceiling is deployment-specific and guessing high turns a slow call into a failed one.
>
> <details><summary>Engineering detail</summary> …the 5 tables, root cause, per-model ceilings,
> what's not in this PR… </details>

## Review comments

Same doctrine, smaller unit. One comment = one claim + the evidence for it, in **five lines or
fewer**. If it needs more, it is a design discussion — say so in one line and take it to the PR
thread or a ticket. Never restate the code you are commenting on back at the author.
